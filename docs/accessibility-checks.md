# 首頁、登入與行程的無障礙複驗

第二輪檢查在 11 個模組的桌面與手機頁面掃描到 0 個 axe 違規。首頁與行程頁各有 2 條規則需要進一步判讀。這次在 Windows 上檢查了這些規則涉及的文字和控制項，並實際操作了鍵盤流程。

## 具名群組與鍵盤

- 首頁的「篩選旅程」與行程頁的「選擇行程日」現在使用具名群組。選取狀態會透過按鈕的 `aria-pressed` 提供給輔助技術。用空白鍵篩選「已確認」後，清單剩下一本符合條件的手札。在示範手札中以 Tab 和空白鍵切換到第 2 天，按鈕的選取狀態也隨之更新。
- 在 1280 與 390 像素寬的瀏覽器中，首次 Tab 會顯示「跳到主要內容」。按 Enter，再按 Tab，焦點落在畫面上的「建立旅程」。開啟登入視窗後，焦點在「關閉」；反向及正向 Tab 都停留在視窗內。原本按 Escape 會將焦點移回文件開頭，現已驗證會回到原來的「建立旅程」按鈕。兩種寬度均可在切換日期後閱讀行程，頁面寬度沒有超出視窗。[鍵盤回歸](../frontend/tests/accessibility-keyboard.spec.ts) · [WAI 對話框鍵盤互動說明](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)
- 在獨立的 Windows Chrome 視窗，另用 Windows UI Automation 讀取文件中的具名「篩選旅程」群組（Group）與「建立旅程」按鈕（Button）。使用平台的 Invoke 操作開啟登入視窗，確認「測試帳號」是 Edit 控制項，密碼 Edit 的 IsPassword 為 true，再用具名「關閉」按鈕的 Invoke 關閉。這一項直接測得作業系統交付輔助技術的名稱、角色、受保護狀態與操作。

## 文字覆蓋圖片與漸層

axe 無法從部分漸層、偽元素與小字縮寫判定對比。複驗使用 Chrome 158 隱藏字形、保留背景、圖片和元件位置，以實際文字範圍內每個背景像素與其計算後的字色比較相對亮度。以下列出該樣本最小的對比值。一般文字門檻為 4.5:1，大字為 3:1。[WCAG 2.2 文字對比](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)

| 讀取位置 | 修正前 | 修正後 |
| --- | ---: | ---: |
| 桌面首頁，封面右下角白色標註 | 3.62:1 | 8.38:1 |
| 手機首頁，封面上的行程天數 | 2.56:1 | 5.27:1 |
| 旅程卡第三位旅伴的單字縮寫 | 4.40:1 | 5.12:1 |
| 行程頁封面標籤、標題、說明、目的地、日期及成員數，桌面 | 8.86:1 | 9.89:1 |
| 同一行程頁封面，手機 | 5.28:1 | 8.93:1 |

首頁其餘待判讀的邀請卡、封面類別、標題、目的地與按鈕，修正後的桌面與手機樣本均達門檻。此範圍的圖片量測採用內建封面與一筆合成旅程。

## 重跑與範圍

在已安裝開發依賴和對應 Playwright 瀏覽器的專案根目錄執行：

```sh
python backend/run_live_acceptance.py --production tests/accessibility-keyboard.spec.ts tests/review-acceptance.spec.ts
```

這些紀錄涵蓋上述頁面的鍵盤操作、讀取順序、名稱、選取狀態與文字對比。其餘主要操作的完整讀屏朗讀、使用者可理解性及所有適用的 WCAG 2.2 AA 準則仍需逐項人工覆核。
